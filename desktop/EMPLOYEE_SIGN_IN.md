# Square employee desktop sign-in (staging candidate)

This integration reuses Buzz's native BB session and local signing key. It is disabled unless both `BUZZ_EMPLOYEE_NATIVE_SIGN_IN=1` and `BUZZ_EMPLOYEE_NATIVE_RELAY_URL=<exact canonical wss://community-host>` are set by the operator. API and browser sender origins stay pinned to the Square BuilderLab staging service and Square staging Dashboard; selecting a community cannot choose an identity server.

For an explicitly selected staging Playpen, set `BUZZ_EMPLOYEE_NATIVE_PLAYPEN_TARGET=<trusted task name>`. This adds fixed `Baggage: kgoose-builderbot-playpen=<task>` only to the pinned public redeem POST, auth-me GET and identity-assertion POST. It replaces ambient routing selection, refuses other origins/actions and preserves the exact signed public URL and body. Both native clients refuse redirects. It never targets the Auth0 token endpoint or a user-selected identity service; leave it unset for normal staging routing.

The employee selects their employer's community and chooses **Sign in with Square**. Native code creates an S256 verifier, independent state and nonce, and a dynamic numeric IPv4 loopback listener. The employee uses their own Square account in the browser and explicitly continues. Only a one-use verifier-bound code and state enter the callback URL. Redeem refuses redirects, verifies the original session's subject and expiry through `/v1/auth/me`, and retains the credential only in the existing native BB session store. No session lifetime is extended.

The desktop requests `/v1/buzz/identity/assertions` with that session and an exact NIP-98 proof signed by its own current Buzz key. That existing service enrolls an absent key and returns a short-lived key-bound relay assertion. The protected native WebSocket upgrade and central human relay HTTP paths attach the assertion while retaining NIP-42/NIP-98 proof. Credentials do not enter renderer command responses. Logout, replaced login, key changes and community changes cancel old authorization; short-lived evidence refresh is bounded. Other communities retain their existing transport.

The initial sign-in surface appears before relay-dependent onboarding. A failed community admission remains retryable. A prepared workspace, received CLI credential, or key enrollment does not by itself mean the employee can message Managerbot.

Before employee acceptance, apply the employee operation schema and server receipt schema, deploy the fenced membership and native handoff services, preserve enterprise revocation authorization time, configure the exact managed workspace and existing Auth0 CTE mount/client secret, and activate only the reviewed ingress and feature flags. The shared private org must retain both Buzz and BuilderLab USER capabilities. The dedicated workspace's `isBuilderlabEnabled=false` is not a denial of the BuilderLab product entitlement.

Managerbot also needs authoritative same-employee key resolution and verified same-person delegated Square OAuth. Those are coordinated follow-up changes; do not seed an employee identity row manually or claim the full message/reply acceptance until they and the live configuration are validated. The client signs the actual external `/api/goose/v1/buzz/identity/assertions` URL; the server's configured proof URL must match exactly.

Local validation uses real loopback HTTP/WebSocket boundaries plus a renderer journey with mocked native IPC; it does not claim live employee authentication. `just desktop-ci`, focused employee transport tests, the shared connector suite, typechecking and the size ratchet pass. Full `just ci` reaches unchanged mobile formatting/dependency errors in this checkout. A debug Tauri client builds through the supported package wrapper; local unit-test sidecar placeholders are not a production release bundle.
