# Chunk 03 -- HOST DNS + CA TRUST

**What it does**

Makes the two dev hostnames resolve to `127.0.0.1` on your own computer, where the VM's NAT forwards
(host 8080 -> guest 80, host 8443 -> guest 443) are waiting. Then, once Caddy exists, copies its
`tls internal` root CA out of the guest and prints -- but does not run -- the command that trusts it.
Everything here happens on the host; nothing on the guest is touched, so no snapshot is involved.

**SOP steps covered:** 10, and the client-address half of 12.3 -- both as reframed by
hardening-spec.md sec-A.3 / Part G items 1-2, which replace the SOP's literal `http://...:3000` and
`ws://` with `https://`/`wss://` on 8443 -- rationale lives there, not here

**Preconditions**

- **Job 1 (hosts entries):** none. It can run before the VM exists, and it is what turns chunk 00's
  two `WARN` rows into `PASS`.
- **Job 2 (CA fetch):** the VM is running (chunk 01, `build-vps-clone.sh`) **and** the stack is up
  with Caddy enabled (chunk 07). The CA is generated by Caddy on first start, so job 2 cannot
  succeed before then -- which is why it is opt-in rather than opt-out.
- Job 2 also needs `ssh -p 2222 dev@127.0.0.1` to work, using the key `build-vps-clone.sh`
  authorised. It connects as `dev` with `sudo docker`, not as root, so it keeps working after SOP
  Step 13.3 disables root login.
- macOS is the executed path. The script implements SOP Step 10's Windows branch as a
  check-plus-instructions, but chunk 00 already limits the chunked path to macOS.

**Run**

Job 1, now:

```bash
cd ~/code/buzz/launchpad/deploy/virtual-box
./host-dns.sh
```

Job 2, after chunk 07 has Caddy running:

```bash
cd ~/code/buzz/launchpad/deploy/virtual-box
./host-dns.sh --ca-only
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain \
  ~/vm-images/buzz-dev-caddy-root.crt
```

The second command is printed by the script with the absolute path filled in; the script never runs
it. `--ca` does both jobs in one pass; `--skip-ca` is the explicit form of the default. Overrides:
`DOMAIN`, `ADMIN_DOMAIN`, `HOSTS_FILE`, `VM_HOST`, `VM_PORT`, `VM_USER`, `CADDY_CA_PATH`, `CA_OUT`.

Exit codes: `0` done · `1` manual edit needed, or a name mapped to the wrong address · `2` VM
unreachable · `3` no Caddy container, i.e. chunk 07 has not run · `4` CA missing or not a PEM.

**Verify**

```bash
grep buzz-vm /etc/hosts
dscacheutil -q host -a name buzz-vm.test | grep ip_address
dscacheutil -q host -a name admin.buzz-vm.test | grep ip_address
cd ~/code/buzz/launchpad/deploy/virtual-box && ./host-dns.sh; echo "exit=$?"
```

Expected -- the marker line appears only if this script did the append, not if you added the entries
by hand from SOP Step 10:

```
# buzz-vm.test -- added by launchpad/deploy/virtual-box/host-dns.sh
127.0.0.1 buzz-vm.test
127.0.0.1 admin.buzz-vm.test
ip_address: 127.0.0.1
ip_address: 127.0.0.1

=== Job 1: hosts entries in /etc/hosts ===
    buzz-vm.test -> 127.0.0.1 (already present)
    admin.buzz-vm.test -> 127.0.0.1 (already present)
    nothing to change.
    resolves: buzz-vm.test -> 127.0.0.1
    resolves: admin.buzz-vm.test -> 127.0.0.1
    next: https://buzz-vm.test:8443 and https://admin.buzz-vm.test:8443/reports once
    chunk 07 is up. Both warn about the certificate until you run:
      ./host-dns.sh --ca-only
exit=0
```

`nothing to change.` on a second run is the convergence check -- a re-run that appends anything is a
bug, not a nuisance.

After chunk 07, that the fetched CA is the one Caddy is actually serving with -- this works whether
or not you have trusted it:

```bash
/usr/bin/curl -s -o /dev/null -w '%{http_code}\n' \
  --cacert ~/vm-images/buzz-dev-caddy-root.crt https://buzz-vm.test:8443/
```

Expect `200`. Then, only after running the `add-trusted-cert` command, the same request with no
`--cacert` must also print `200`:

```bash
/usr/bin/curl -s -o /dev/null -w '%{http_code}\n' https://buzz-vm.test:8443/
```

A `curl: (60)` there means the trust command was not run, or was run against the login keychain.

**Rollback**

Job 1 -- remove both entries and the marker comment, then drop the cache (macOS `sed -i` needs the
empty argument):

```bash
sudo sed -i '' '/buzz-vm\.test/d' /etc/hosts
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
```

Job 2 -- nothing is installed unless you ran the printed command yourself. To undo that, and only
then delete the file:

```bash
sudo security remove-trusted-cert -d ~/vm-images/buzz-dev-caddy-root.crt
rm ~/vm-images/buzz-dev-caddy-root.crt
```

Untrusting needs the same file that was trusted, which is why the fetch keeps a copy on disk rather
than piping straight into the keychain. No VM snapshot applies -- nothing in the guest changes.

**Traps**

- Job 2 has a hard ordering dependency: the local CA does not exist until Caddy has started at least once, so it exits `3` before chunk 07 -- run the chunk twice, not once (hardening-spec.md sec-A.3).
- `docker compose down -v` destroys the `buzz-caddy-data` volume and Caddy mints a **new** CA, silently invalidating the trusted root; `remove-trusted-cert` the old one first, then re-fetch and re-trust (`deploy/compose/compose.caddy.yml` volumes).
- The desktop app is the likelier failure, not the browser: Tauri's Rust TLS stack validates against the system store with no "proceed anyway" prompt, so an untrusted CA is a refused `wss://` connection rather than a warning (SOP Step 12.3 as corrected by hardening-spec.md sec-A.3).
- Firefox keeps its own trust store and ignores the System keychain entirely, so it still warns after the trust command succeeds (SOP Step 10 browser check).
- Homebrew's `curl` is OpenSSL-linked and does not read the keychain either -- use `/usr/bin/curl` for the verify above, or a pass will look like a failure (hardening-spec.md sec-A.3).
- Every URL needs `:8443` because macOS forbids non-root binds below 1024; the guest side is really 443, so container config stays production-identical (`build-vps-clone.sh` port-forward comment, hardening-spec.md sec-A.3).
- A name already mapped to some other address is an error, not something to append past: the resolver may take either line and the failure surfaces as a relay `Host` rejection (SOP Step 10; relay-build-list.md on `RELAY_URL`).
- macOS caches the failed lookup, so an edit made by hand -- rather than by this script -- can keep failing for minutes until `dscacheutil -flushcache` (SOP Step 10).
- On Windows, Notepad opened without "Run as administrator" appears to save and quietly discards the change; the script refuses to claim success and exits `1` instead (SOP Step 10).
- Rebuilding the VM changes the host key for `[127.0.0.1]:2222` and ssh then refuses to connect: `ssh-keygen -R '[127.0.0.1]:2222'` (chunk 01 opens with `unregistervm --delete`).
- The Windows branch is unverified, like every **On Windows** block in the SOP -- treat it as documented behaviour, not as executed (SOP "what has and has not been proven").
