# Chunk 07 — up

**What it does.** Brings the whole stack up on all three compose files (so Caddy is included and the
relay's port 3000 stays unpublished), then verifies it in ways that can actually fail — the community
binding, a real WebSocket upgrade, the relay-served surfaces, and the memory footprint.

**SOP steps covered:** 8 and 9, corrected for TLS per `hardening-spec.md` §A.3 and §B2. Rationale
lives there, not here.

## Preconditions

- Chunk 06 has run: `/opt/buzz/compose/.env` exists, mode 0600 root, plus `compose.cohort.yml` and
  `/opt/buzz/cohort/Caddyfile`.
- Chunk 05 has run: the seven upstream files are in `/opt/buzz/compose/`.
- Chunk 04 has run: Docker ≥ Compose 2.24.4 (the `!reset` tag needs it).
- Roughly 1.2 GB of image pulls on first run.

## Run

```bash
./deploy run 07
```

## Verify

The playbook asserts all of this itself and fails the run if any of it is wrong. To check by hand
afterwards:

```bash
./deploy verify
```

Or the two assertions that matter most, from the host:

```bash
# 1. The WebSocket upgrade. --http1.1 is NOT optional -- see Traps.
curl -sk -i -N --http1.1 --max-time 8 \
  --resolve buzz-vm.test:8443:127.0.0.1 \
  -H "Connection: Upgrade" -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Version: 13" -H "Sec-WebSocket-Key: AAAAAAAAAAAAAAAAAAAAAA==" \
  https://buzz-vm.test:8443/ | head -1
# expect: HTTP/1.1 101 Switching Protocols

# 2. The community must carry the port.
ssh -p 2222 dev@127.0.0.1 "cd /opt/buzz/compose && sudo docker compose --env-file .env \
  -f compose.yml -f compose.caddy.yml -f compose.cohort.yml \
  exec -T postgres psql -U buzz -d buzz -tAc 'select host from communities;'"
# expect: buzz-vm.test:8443
```

Measured on 2026-08-12, TLS path, image `sha-96ae141`: all six containers up, community
`buzz-vm.test:8443`, `101` on the correct Host, swap untouched.

## Rollback

```bash
./deploy restore pristine     # back to a bare VM, then re-run 04-07
```
Or to keep the machine and just reset the stack:
```bash
ssh -p 2222 dev@127.0.0.1 "cd /opt/buzz/compose && sudo docker compose --env-file .env \
  -f compose.yml -f compose.caddy.yml -f compose.cohort.yml down -v"
```
`down -v` destroys the volumes, so Postgres, MinIO and the Caddy CA all go. `.env` survives, and
because secrets are generate-once the next chunk 07 reuses the same identities.

## Traps

- **`--http1.1` on the WebSocket check is load-bearing.** Over TLS, curl negotiates HTTP/2 via ALPN,
  and HTTP/2 deleted the `Connection: Upgrade` mechanism — so the relay sees a plain GET, answers
  `200` with the NIP-11 document, and the check passes while proving nothing. Verified 2026-08-12:
  identical request returns `101` with the flag and `200` without it. This trap does not exist in the
  SOP because the SOP tested plaintext HTTP/1.1 on port 3000; TLS introduced it.
- **`/health`, `/_liveness` and NIP-11 return `200` even when the address is completely wrong**, so a
  relay refusing every client passes all three. Only the upgrade proves the binding (SOP Step 8.2).
- **The relay's own refusal is invisible from outside.** Caddy rejects an unknown SNI at the TLS
  handshake (`curl` reports `000`), so `relay: no community is configured for this host` can only be
  observed by bypassing Caddy on the Docker network. Both layers are asserted; they prove different
  things.
- **Caddy declares no healthcheck**, so `docker compose ps --format json` reports `Health: ""` for it
  even though `up --wait` prints `Healthy`. An assertion demanding `healthy` for every service fails
  on a good stack — verified 2026-08-12.
- **A bare `docker compose` command here acts on a different stack.** Without all three `-f` files you
  get no Caddy, no network alias, and a relay published on 3000 — the failure `hardening-spec.md` §B2
  describes.
- **The community host keeps its `:8443`.** `normalize_host` strips only a trailing `:443` or `:80`
  (`crates/buzz-core/src/tenant.rs:121`), so dev's community is `buzz-vm.test:8443` and production's
  is a bare domain. Every Host header must match byte-for-byte after that normalization.
