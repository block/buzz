# Chunk 07 — up

**What it does.** Brings the whole stack up on the compose file set `buzz_compose_files` resolves to
— by default `compose.yml` + `compose.cohort.yml`, with the relay reachable directly on plaintext
3000 — then verifies it in ways that can actually fail: the community binding, a real WebSocket
upgrade, the relay-served surfaces, and the memory footprint.

**SOP steps covered:** 8 and 9. The default addressing is the SOP's own plaintext `ws://…:3000`. The
three-file Caddy + `tls internal` variant (`hardening-spec.md` §A.3, §B2) is retained as an opt-in
profile. Rationale for both lives in the SOP, not here.

## Preconditions

- Chunk 06 has run: `/opt/buzz/compose/.env` exists, mode 0600 root, plus `compose.cohort.yml` (and
  `/opt/buzz/cohort/Caddyfile`, which only the experimental profile mounts).
- Chunk 05 has run: the seven upstream files are in `/opt/buzz/compose/`.
- Chunk 04 has run: Docker ≥ Compose 2.24.4 (the `!reset` tag in the experimental profile needs it).
- Chunk 02 created the `relay` NAT forward `127.0.0.1:3000 -> guest 3000`. Without it the stack comes
  up correctly and nothing on the host can reach it.
- Roughly 1.2 GB of image pulls on first run.

## Run

```bash
./deploy run 07
```

## Verify

The playbook asserts all of this itself and fails the run if any of it is wrong — under the
experimental profile. On the plaintext default some of its assertions are wrong for the topology
rather than wrong about it (Traps). To check by hand afterwards:

```bash
./deploy verify   # scripts/verify.sh also still hardcodes the three-file invocation
```

Or the two assertions that matter most, from the host:

```bash
# 1. The WebSocket upgrade.
curl -s -i -N --max-time 8 \
  -H "Host: buzz-vm.test:3000" \
  -H "Connection: Upgrade" -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Version: 13" -H "Sec-WebSocket-Key: AAAAAAAAAAAAAAAAAAAAAA==" \
  http://127.0.0.1:3000/ | head -1
# expect: HTTP/1.1 101 Switching Protocols

# 2. The community must carry the port.
ssh -p 2222 dev@127.0.0.1 "cd /opt/buzz/compose && sudo docker compose --env-file .env \
  -f compose.yml -f compose.cohort.yml \
  exec -T postgres psql -U buzz -d buzz -tAc 'select host from communities;'"
# expect: buzz-vm.test:3000
```

Under the experimental TLS profile the same two become — note `--http1.1`, which is load-bearing
there and only there (Traps):

```bash
curl -sk -i -N --http1.1 --max-time 8 \
  --resolve buzz-vm.test:8443:127.0.0.1 \
  -H "Connection: Upgrade" -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Version: 13" -H "Sec-WebSocket-Key: AAAAAAAAAAAAAAAAAAAAAA==" \
  https://buzz-vm.test:8443/ | head -1
# expect: HTTP/1.1 101 Switching Protocols

ssh -p 2222 dev@127.0.0.1 "cd /opt/buzz/compose && sudo docker compose --env-file .env \
  -f compose.yml -f compose.caddy.yml -f compose.cohort.yml \
  exec -T postgres psql -U buzz -d buzz -tAc 'select host from communities;'"
# expect: buzz-vm.test:8443
```

Measured on 2026-08-12, experimental TLS profile, image `sha-96ae141`: all six containers up,
community `buzz-vm.test:8443`, `101` on the correct Host, swap untouched. The plaintext default was
verified on 2026-08-11 by the SOP's own Step 8/9 commands, not by this play — see Traps.

## Rollback

```bash
./deploy restore pristine     # back to a bare VM, then re-run 04-07
```
Or to keep the machine and just reset the stack — pass the same `-f` set the stack was brought up
with, adding `-f compose.caddy.yml` under the experimental profile:
```bash
ssh -p 2222 dev@127.0.0.1 "cd /opt/buzz/compose && sudo docker compose --env-file .env \
  -f compose.yml -f compose.cohort.yml down -v"
```
`down -v` destroys the volumes, so Postgres, MinIO and — under the experimental profile — the Caddy
CA all go. `.env` survives, and
because secrets are generate-once the next chunk 07 reuses the same identities.

## Traps

- **Two topologies, one variable.** `buzz_compose_files` is derived from `buzz_tls_mode`
  (`group_vars/all.yml`): `none` — the dev default — gives `compose.yml` + `compose.cohort.yml` with
  the relay published on 3000, anything else adds `compose.caddy.yml`. Production is never `none`;
  its `ports: !reset []` is §B2's required control 1 and `ufw` cannot substitute for it.
- **The play itself still asserts the Caddy topology.** `relay_up` requires that no service publishes
  a port other than 80/443, probes every surface over `https://…:443`, and expects Caddy in
  `docker compose ps` — all correct for the experimental profile and all failing on the plaintext
  default, where the relay legitimately publishes 3000. Re-scoping that assertion is a change to a
  stated control, so `hardening-spec.md` §B2 has to carry the dev carve-out first ("the SOP changes
  first"). Until then, drive the default path with SOP Steps 8 and 9 directly.
- **`--http1.1` on the WebSocket check is load-bearing under the TLS profile.** Over TLS, curl
  negotiates HTTP/2 via ALPN, and HTTP/2 deleted the `Connection: Upgrade` mechanism — so the relay
  sees a plain GET, answers `200` with the NIP-11 document, and the check passes while proving
  nothing. Verified 2026-08-12: identical request returns `101` with the flag and `200` without it.
  On the plaintext default curl speaks HTTP/1.1 anyway and the flag is harmless but unnecessary.
- **`/health`, `/_liveness` and NIP-11 return `200` even when the address is completely wrong**, so a
  relay refusing every client passes all three. Only the upgrade proves the binding (SOP Step 8.2).
- **The relay's own refusal is visible on the default path and hidden under the TLS profile.** With
  no proxy, a wrong `Host` gets `relay: no community is configured for this host` straight from the
  relay. Under the TLS profile Caddy rejects an unknown SNI at the handshake first (`curl` reports
  `000`), so the relay's refusal can only be observed by bypassing Caddy on the Docker network. Both
  layers are asserted there; they prove different things.
- **Caddy declares no healthcheck**, so under the TLS profile `docker compose ps --format json`
  reports `Health: ""` for it even though `up --wait` prints `Healthy`. An assertion demanding
  `healthy` for every service fails on a good stack — verified 2026-08-12.
- **A bare `docker compose` command here acts on a different stack.** Pass exactly the `-f` set
  `buzz_compose_files` resolves to. Dropping `compose.cohort.yml` loses the network alias; dropping
  `compose.caddy.yml` under the TLS profile republishes 3000 — the failure `hardening-spec.md` §B2
  describes.
- **The community host keeps its port.** `normalize_host` strips only a trailing `:443` or `:80`
  (`crates/buzz-core/src/tenant.rs:121`), so dev's community is `buzz-vm.test:3000` (`:8443` under
  the TLS profile) and production's is a bare domain. Every Host header must match byte-for-byte
  after that normalization.
- **Reaching the stack from the host needs the `relay` NAT forward.** `127.0.0.1:3000 -> guest 3000`
  is created by `virtual-box/build-vps-clone.sh`; a VM built before that rule existed has only
  `2222`, `8080` and `8443`, and every host-side check here times out while the guest is perfectly
  healthy. Add it to a running VM without a rebuild:
  `VBoxManage controlvm buzz-dev natpf1 "relay,tcp,127.0.0.1,3000,,3000"`.
