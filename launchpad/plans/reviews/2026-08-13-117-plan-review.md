## Blocker 1 — the `contain.Finding` conversion never maps `entry_point`, and `evidence` is droppable with it

**Lands on:** STEP 1 (plan line 195). Inherited by STEP 3's conversion (line 341) and
STEP 9's conversion control (line 555).

**Defect.** The mapping at plan lines 195–208 fixes six fields: `anchor`, `severity`,
`dimension`, `defect`, `failure`, `evidence`. `file`, `line` and `finding_id` are all
derivable from rules stated elsewhere. `entry_point` is neither mapped nor derivable — it
is the only field in `contain.Finding` with nowhere to go, and plan line 190 states the
conversion exists precisely because "defining `entry_point` without defining the
conversion is what leaves the deterministic catches stranded."

The drop is legal twice over: `entry_point` is declared optional (line 172), and
`evidence` is required only "whenever `entry_point` is set" (line 177). So a converter
omitting `entry_point` may also omit `evidence`, and `findings.validate` accepts it.
STEP 9's conversion control asserts `dimension`, `anchor`, `severity` and `evidence` —
not `entry_point`.

**Concrete failure.** A PR body carrying an injection attempt produces
`contain.Finding("injection_attempt", "pr_body", "<excerpt>")`. The converter emits
`{"dimension":"containment","severity":"Blocker","anchor":"pr","file":null,"line":null,
"defect":"…","failure":"…","finding_id":"…"}`. Every `validate` rule passes; the STEP 9
control passes. The published Blocker says an injection attempt occurred somewhere in
this pull request with **no surface named, no excerpt, no file and no line** — anchor
`pr` having already removed the last two. That is the detected-then-dropped case
`CONTAINMENT.md:129-131` calls "worse than one never detected, because it reads as a
clean review."

It is also a regression against committed behaviour: `review.py:65` prints
`Entry point: \`{finding.entry_point}\`` for every containment finding today.

**Fix.** Add an `entry_point` row to the mapping carrying `contain.Finding.entry_point`
unchanged. Make `entry_point` and `evidence` **required** whenever `dimension` is
`containment`, not merely conditionally required on each other. Add `entry_point` to
STEP 9's conversion assertions.

## Blocker 2 — `finding_id` excludes `entry_point` and `evidence`, so containment findings of the same kind collide on one id

**Lands on:** STEP 1 (plan line 215). Consumed by #118's one-verdict-per-finding
guarantee (line 217).

**Defect.** `finding_id` is "a truncated hash of (dimension, anchor, file, line,
defect)". For every containment finding four of those five are constants — `dimension` is
`"containment"`, `anchor` is `"pr"`, `file` and `line` are `null`. The fifth, `defect`,
is "derived from `kind`" (line 203), a function of kind alone with three possible values.
So all containment findings of a given kind share one id. `contain.py:221` keys its own
dedupe on `(kind, entry_point, evidence)` — the plan's id drops two of those three.

**Concrete failure.** Narrowest input, a single PR body containing both a case-variant
and a letter-spaced delimiter:

```
contain.find_lookalikes -> 2 finding(s) (after its own _dedupe):
   kind= delimiter_lookalike | ep= pr_body | evidence= see <<<buzz-untrusted for context, and also
   kind= delimiter_lookalike | ep= pr_body | evidence= t, and also <<< B U Z Z - U N T R U S T for

plan finding_id = truncated hash of (dimension, anchor, file, line, defect):
    df2ee371fe38 <- delimiter_lookalike pr_body
    df2ee371fe38 <- delimiter_lookalike pr_body

distinct findings: 2 | distinct finding_ids: 1
```

Two Blockers the containment layer deliberately kept apart carry one id. Plan line 217
says the id "lets #118 attach exactly one verdict per finding and makes its dedupe
visible rather than silent" — so #118 attaches one verdict to two attacks, or dedupes by
id and silently drops one. Both are the swallowed attack. The same collision occurs
across surfaces: an `injection_attempt` in `pr_body` and one in `pr_diff` are one id.

This survives a fix to Blocker 1 on its own — carrying `entry_point` in the record does
not change the id unless the id's inputs change.

**Fix.** Include `entry_point` and a digest of `evidence` in the id inputs for
containment findings, or hash `(dimension, entry_point, kind, evidence)` for them. Add a
control asserting two `delimiter_lookalike` findings from one entry point get distinct
ids.

## Blocker 3 — `launchpad-26/buzz` is public, so the repo probe cannot distinguish a broken credential from a missing PR

**Lands on:** STEP 3 (plan line 318).

**Defect.** STEP 3 classifies into three states with `GET /repos/{o}/{r}` as the
discriminator: "the PR endpoint 404s AND `GET /repos/{o}/{r}` succeeds, so the credential
can see the repo and the PR genuinely is not in it". Stated purpose, plan lines 328-330:
"Without the repo probe this module would report a credential failure as a fact about
someone's pull request." The repo is public, so the probe answers 200 to a caller with no
credential at all:

```
=== repo visibility ===
{"isPrivate":false,"visibility":"PUBLIC"}

=== UNAUTHENTICATED (simulates a revoked/absent credential) ===
repo probe   : 200
PR 999999    : 404
PR 86 (real) : 200
```

**Concrete failure.** The Actions token's `contents: read` is revoked or expires.
`GET /repos/launchpad-26/buzz` returns 200 — the repo is public and the endpoint needs no
auth. `GET .../pulls/42` returns 404. The classifier reads "repo succeeds AND PR 404s"
and exits with a reason naming **the pull request as absent**. That is verbatim the
misclassification the probe was added to prevent, now carrying a false air of having been
checked. The premise at plan lines 325-329 — "a token that loses read access presents
EXACTLY as 'PR 42 does not exist'" — is true for a private repo and false for this one,
where losing read access does not stop the read at all.

**Fix.** Replace the repo probe with an **identity** probe (`GET /user`, or
`gh auth status`), which distinguishes a working credential from a broken one
independently of what any repo's visibility permits. Keep the repo call as a secondary
check and state that on a public repo the "cannot see it" branch is unreachable via it.

## Medium 10 — `evidence` is stored post-escape, but the renderer #119 is bound to call escapes again

**Lands on:** STEP 1's conversion (plan line 206).

**Defect.** The conversion says `evidence` is "rendered post-escape, per `review.py`'s
existing rule". `review.py`'s rule is not that evidence is *stored* escaped — it escapes
**at render time** from a raw-evidence `Finding`:

```python
# review.py:71-73
lines.append(fence_for(finding.evidence))
lines.append(escape(finding.evidence))
lines.append(fence_for(finding.evidence))
```

Every `contain.Finding` in the system carries raw evidence (`contain.py:151`,
`detect.py:106`). #117's records would be the only ones carrying escaped evidence, and
`CONTAINMENT.md:219` binds #119 to `review.render_review`.

**Concrete failure.** A containment finding whose excerpt contains `~` — the escape
character — is stored as `~~`. Rendered through `render_review` it publishes as `~~~~`; a
literal `BUZZ-UNTRUSTED` in the excerpt publishes as `~~U`, and a single `unescape`
recovers `~U`, not the token. Nothing is dropped, so this is not the swallowed-attack
case, but the published excerpt no longer matches what the author wrote and an adjudicator
comparing evidence to the diff finds no match. `fence_for` is also not carried into #117's
contract, so an excerpt containing a triple backtick breaks out of a fixed fence in any
consumer that does not re-derive it.

**Fix.** State the escape state explicitly: either "`evidence` carries the raw excerpt;
consumers escape at render, as `review.py` does" — which keeps every `Finding` in the
system uniform and is what #119's plan already assumes — or "`evidence` is already
escaped; consumers must not escape again", and in that case say so in the row
`CONTAINMENT.md`'s stage table gains per STEP 1's done-when so #119 reads it.
