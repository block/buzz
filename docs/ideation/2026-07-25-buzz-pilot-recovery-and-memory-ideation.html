Buzz Pilot Recovery And Memory

Ranked next moves after the local Buzz pilot came up once, shut down, and left the Mac app running. The center question is whether the earlier pilot community can be recovered as useful agent memory, and what to do next without losing confidence.

Date: 2026-07-25 Topic: buzz-pilot-recovery-and-memory Focus: local pilot continuity, old community recovery, agent memory Mode: repo-grounded

Grounding Context

Buzz stores conversation state as signed events in a relay-backed event log. In this local setup, the backing services are Docker Compose services, and the durable data lives in named volumes such as buzz-postgres-data. Docker's own Compose docs say named volumes are not removed by default on docker compose down, but are removed by --volumes.

Local metadata inspection found active Docker services for Postgres, Redis, MinIO, Prometheus, Adminer, and Keycloak. The named volumes buzz-postgres-data, buzz-minio-data, and buzz-prometheus-data exist.

The database currently has two meaningful local communities. localhost:3000 has 2 channels and 44 events: codex-pilot-smoke and pilot-demo. localhost:3030 has 4 channels and 176 events: buzz-pilot, install-support, repo-review, and agent-runs.

Port inspection found 3000 still held by a Node process, while 3030 and 8088 were no longer listening. That means the old community is likely still stored, but it is not currently reachable through the normal old authority because the relay is not running on localhost:3000.

The repo's seed script intentionally treats loopback authorities as distinct hosts. Because localhost:3000 and localhost:3030 map to distinct community rows, switching ports can feel like memory loss even when the same Postgres volume still contains both logs.

Topic Axes

  • Recoverability: how to get the prior conversation back without data mutation.
  • Continuity: how to keep one stable pilot identity and community going forward.
  • Visibility: how to make active and blocked agent work obvious.
  • Memory value: how to turn Buzz threads into reusable agent context.
  • Safety: how to avoid losing data or leaking credentials while experimenting.

Ranked Ideas

  1. 1. Recover old community by replaying its original authority
  2. 2. Make a pilot continuity runbook before more feature work
  3. 3. Promote Buzz threads into a memory index, not raw memory
  4. 4. Stabilize one pilot community and freeze the other as an archive
  5. 5. Add a daily agent pulse that mirrors only summaries to Slack
  6. 6. Create a backup-first migration experiment for host/port moves

1. Recover old community by replaying its original authority

Axis: Recoverability

Description: Treat localhost:3000 as the old community's key, not just a port. Free port 3000, stop any competing relay, and start Buzz on the default authority so the desktop and CLI resolve the same community row that already has codex-pilot-smoke and pilot-demo.

Basis: direct: local DB metadata shows localhost:3000 has 2 channels and 44 events; repo seed logic creates distinct host rows for localhost:3000 and localhost:3030.

Rationale: This is the highest-confidence way to get the old conversation back because it avoids rewriting event ownership, channel IDs, or community foreign keys.

Downsides: Requires stopping or moving the Node app on port 3000. It may be inconvenient while Amancha Wedding is active.

Confidence: 90%

Complexity: Low

2. Make a pilot continuity runbook before more feature work

Axis: Continuity

Description: Write a short operator runbook that answers: which port is canonical today, which community should agents write to, how to restart safely, how to check event counts, how to avoid dev-reset, and how to back up the database volume before risky experiments.

Basis: direct: local notes already record port collision, alternate port setup, channel IDs, CLI smoke evidence, and the distinction between the app and the relay.

Rationale: A runbook turns fragile terminal memory into a repeatable operating surface. It is the fastest way to prevent "where did my memory go?" from recurring.

Downsides: It is not glamorous, and it will need updates as the pilot settles.

Confidence: 86%

Complexity: Low

3. Promote Buzz threads into a memory index, not raw memory

Axis: Memory value

Description: Define "agent memory" as an index of durable Buzz task threads plus closing summaries, not as every message being automatically trusted. Agents should read thread roots and closeouts through buzz-cli, then cite the thread/event IDs they relied on.

Basis: reasoned: Buzz's event-log model makes retrieval and attribution strong, but raw chat is noisy; a curated memory index gives agents enough context without making every transient message canonical.

Rationale: This preserves the thing you hoped for, "my conversations become memory," while avoiding the trap where unresolved setup chatter becomes false institutional knowledge.

Downsides: Requires discipline: every useful thread needs a closeout that says what is true, what changed, and what is still uncertain.

Confidence: 82%

Complexity: Medium

4. Stabilize one pilot community and freeze the other as an archive

Axis: Continuity

Description: Pick one canonical pilot authority for new work. Keep the other community read-only/archive until a proper migration path exists. For example: continue Day 1 on localhost:3030, but temporarily restart localhost:3000 only to read/export the older demo conversations.

Basis: direct: the DB currently contains both communities with different channel sets and event counts.

Rationale: This avoids accidental split-brain while preserving prior context.

Downsides: The archive is not visible from the active community unless linked or exported.

Confidence: 80%

Complexity: Low

5. Add a daily agent pulse that mirrors only summaries to Slack

Axis: Visibility

Description: Keep Buzz canonical, but have a daily or per-task pulse summarize active threads to Slack: active, blocked, changed artifacts, and needs Steve. Do not mirror raw logs or secrets.

Basis: direct: the Day 0 note already defines a webhook-first Slack visibility track; external: Slack incoming webhooks are designed for simple app-to-channel posting, and Slack Web API posting can be added later for richer threading.

Rationale: This makes agent work visible without turning Slack into the memory database.

Downsides: Adds another inbox if summaries are too frequent or too vague.

Confidence: 74%

Complexity: Medium

6. Create a backup-first migration experiment for host/port moves

Axis: Safety

Description: Before any aliasing or merge attempt, take a Postgres backup, then test a scripted migration in a disposable copy. The goal would be to move or duplicate the old localhost:3000 community into the canonical pilot authority without corrupting signed event expectations or foreign-key relationships.

Basis: direct: the communities table has one unique host per community and many dependent tables; Docker Compose uses named volumes for persistence.

Rationale: This is the path if preserving one unified community becomes more valuable than keeping old and new communities separate.

Downsides: It is easy to over-invest here too early. Read/export first; migrate only if the old conversations are actually valuable enough.

Confidence: 65%

Complexity: High

Rejection Summary

#IdeaReason Rejected
1Merge localhost:3000 and localhost:3030 immediately in-placeToo risky without backup and schema-specific migration; many tables reference community_id.
2Treat the running Mac app as the memory storeIncorrect model; the app is a client, while durable memory is in relay/Postgres events.
3Keep switching ports opportunisticallyCreates split-brain local communities and makes retrieval feel random.
4Use dev-reset to get unstuckDangerous for this pilot because it intentionally deletes development data and volumes.
5Mirror all Buzz messages to SlackLeaks too much context and makes Slack an accidental second memory store.
