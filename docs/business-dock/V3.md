# Business Dock V3.2 — Production Identity and Embed Sessions

Recorded on 2026-08-20. V3.2 promotes the Business Auth Gateway to the
production identity boundary. The V3.1 Node/SQLite implementation remains a
test-only compatibility fixture and is not production authority.

## 1. Executive decision

- Web keeps two native Authentik clients and two independent application
  sessions.
- macOS Workbench authenticates with system-browser OIDC code + PKCE. The
  authenticated Desktop calls the Gateway with its Workbench access token,
  proves its local Buzz device identity, and requests a one-time Embed Session.
- Business redeems that ticket inside its own WKWebView origin and creates its
  own host-only HttpOnly session. No Authentik token or cookie crosses the
  iframe boundary.
- Windows retains the same Embed Bootstrap candidate but is `NOT TESTED —
  RELEASE BLOCKED` until the packaged WebView2 checklist passes.

This is deliberately not native Business SSO on macOS. System-browser and
WKWebView cookie jars are not assumed to be shared, and no cookie copying,
private WebKit API, token handoff, or relaxed cookie setting is permitted.

## 2. Production authority

`services/business-auth-gateway` is a Rust/Axum/PostgreSQL service. It owns:

- enterprise OIDC subjects and Workbench sessions;
- Buzz identity/device bindings and signed challenges;
- one-time Embed Sessions;
- independent Business sessions;
- append-only security audit events.

It validates Authentik JWT signature, issuer, expiry, audience or authorized
party, client, and subject against discovery/JWKS metadata. Configuration fails
closed before the listener starts.

## 3. Device binding

The first Gateway call resolves the enterprise user but cannot issue an Embed
Session until the current Buzz public key and device are bound. The Gateway
creates a short-lived canonical challenge; Desktop signs it with the existing
Nostr identity command and returns only the public proof. Challenges are
single-use, hashed, audience-bound, device-bound, and replay/expiry safe.

Revoking a binding atomically revokes its active Embed and Business sessions
and records the cascade in the security audit.

## 4. Embed Session

An Embed ticket contains 256 bits of randomness encoded with unpadded Base64URL.
Only SHA-256 is stored. It expires after 30 seconds, is bound to the exact
deployment, `business-dock` audience, Workbench session, binding, and validated
Business target, and is limited to 10 issuances per Workbench session per
minute.

The production Desktop flow is:

1. Workbench completes Authentik OIDC in the system browser.
2. Desktop sends the Workbench access token to the Gateway over trusted HTTPS.
3. Gateway validates the JWT and active device binding.
4. Gateway returns a one-time Business bootstrap URL.
5. WKWebView navigates to `/embed/bootstrap`; PostgreSQL atomically consumes
   the ticket exactly once.
6. Business creates an independent server-side session, sets a host-only
   `__Host-` cookie, and redirects to the validated `/embed/` target.

The ticket query parameter must be excluded from reverse-proxy access logs.
Bootstrap and session responses are `no-store`.

## 5. Business session and CSRF

The Business session token is opaque, stored only as a hash, and delivered as
`HttpOnly; Secure; SameSite=None; Partitioned; Path=/` without a `Domain`
attribute. It is never exposed to frontend JavaScript. State-changing Business
requests require an exact allowed `Origin` and a matching CSRF token.
`GET /api/session` rotates the CSRF token and returns it to the authenticated
Business origin; the frontend keeps it in memory only. The token is not an
authentication credential and never crosses the Bridge, URL or local storage.

## 6. Logout semantics

The Desktop toolbar exposes three explicit scopes:

- **Business only** revokes the current Business session and preserves the
  Workbench and Authentik SSO sessions.
- **Workbench only** revokes that Workbench session and its active Embed and
  Business children, while preserving the Authentik SSO session.
- **All enterprise apps** performs the same local cascade and starts Authentik
  RP logout.

Authentik back-channel logout validates a signed logout token and revokes by
`sid` when present. A standards-compliant token without `sid` falls back to the
issuer-scoped `sub`; it never performs an unscoped subject lookup. Desktop also
clears and notifies the Business iframe when Workbench authentication is lost.

## 7. Audit and operations

Security audit rows are append-only at both trigger and runtime-role levels.
The service records OIDC acceptance/rejection, binding challenge and result,
ticket issuance/consumption/replay/rate limiting/revocation, Business session
lifecycle, all logout scopes, back-channel logout, and cleanup expiry events.
It stores identifiers, bounded reason codes, hashes/short forms, request facts,
and trace IDs—not access tokens, cookies, ticket values, PKCE material, or
secrets.

The expiry worker marks stale challenges and sessions and adds lifecycle audit
events. `--cleanup-once` is available for an operational sweep. Migration 0001
is forward-only; rollback is application rollback plus a database snapshot or
restore, never an automatic destructive down migration.

## 8. Deployment boundary

The deployment example separates a migration owner from a least-privilege
runtime role. Runtime receives normal CRUD only on authority tables and
`SELECT, INSERT` on the audit table. Secrets are injected externally;
`.env.example` contains no production secret. Production requires an
organization-trusted HTTPS certificate, strict allowed origins, exact issuer
and client configuration, and reverse-proxy query-log exclusion for bootstrap.

The macOS acceptance script can start an isolated Relay/PostgreSQL/Redis/MinIO
stack from clean volumes, migrate it, wait for readiness, launch the isolated
packaged app, and clean up processes without touching normal Buzz data.

## 9. Verification status

Automated evidence currently passes:

- Gateway Rust unit, JWT-negative-path, and PostgreSQL security integration
  suites;
- concurrent ticket redemption with exactly one successful consumer;
- signed binding, replay, expiry, target, deployment, rate-limit, cascade,
  logout, back-channel, append-only audit, cleanup, and disabled-user cases;
- Desktop full unit suite and static Business Dock E2E;
- production Compose readiness and least-privilege audit grants;
- clean isolated macOS Relay bootstrap through packaged app launch.

The precise platform evidence and any remaining manual gate are recorded in
`auth-poc-matrix.md`. Windows remains release-blocking until tested on Windows.

## 10. Upstream Buzz impact

The change remains a narrow wrapper around the existing application. It adds
Workbench authentication, Business Dock session transport, Gateway calls,
deployment files, and acceptance tooling. It does not replace the Buzz Nostr
identity/channel model, navigation, dirty guard, onboarding, or V1/V2 business
resource behavior. The local device proof reuses the existing Nostr signer.

## 11. Out of scope

V3.2 does not add RBAC/group synchronization, ERP writes, MCP tools, agent
business queries, Windows support claims, or a general Desktop network proxy.
The next phase is `V4：只读 Business MCP 与 Agent 业务查询`.
