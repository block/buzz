# Android push enrollment requires hardware key attestation of a trusted operating system

The push gateway's enrollment endpoints are public and have no other authentication, so an installation proves it is the gateway's app on real hardware before it can enroll: App Attest on iOS, Android Key Attestation on Android. The gateway verifies Key Attestation offline, as it does App Attest, against Google's attestation roots and its published revocation list (the gateway's one periodic online fetch). The app identity in the attestation (package name and signing certificate) is filled in by the operating system, not the secure hardware, so it proves only as much as that operating system can be trusted. The gateway therefore accepts an attestation only when the hardware reports a locked bootloader and either a verified boot state of Verified (the phone maker's OS), or SelfSigned with a verified boot key on a list the operator configures. The list is empty by default, so a default gateway accepts stock Android only; an operator can add, for example, GrapheneOS's published per-device boot keys. Phones without hardware-backed attestation get no push; there is no software fallback. Every later installation call is signed with the attested key, as App Attest assertions are on iOS. Enrollment keeps its existing challenge quotas and adds a rate limit per attested key.

## Considered options

- **Play Integrity.** It would send Google a request for every enrollment, which works against Buzz's privacy goals, and it adds Google's server API and its quotas as a dependency.
- **Accept any locked SelfSigned phone.** Anyone can install a self-built OS with their own boot key and relock the bootloader, and that OS can claim to be our app. Attestation carries no stable device id and each enrollment makes a fresh key, so one such phone could script unlimited enrollments, bounded only by the deployment-wide challenge quota, whose exhaustion stops everyone else enrolling.
- **Stock Android only.** Simpler, with no list to maintain, but it excludes GrapheneOS, which Buzz's privacy goals make worth supporting.
- **Accept any boot state.** It would let more phones enroll, but a rooted phone could then claim to be any app, which leaves the endpoints open to the abuse attestation is meant to stop.
