# Business Core B1 — implementation record

> B1 remains authoritative for master data, enterprise users, roles and all six
> scope dimensions. B2 consumes those UUIDs and decisions without duplicating
> identity or scope data. See [B2.md](B2.md).

## Result

B1 establishes the first authoritative Business System module without
expanding Buzz, Agent, MCP, or Workbench V6 abstractions. The implementation is
a PostgreSQL-backed modular monolith in `services/business-core` and reuses the
existing EnterpriseUser authority from Business Auth Gateway.

This is production-shaped code, not a claim that a real company dataset has
already been loaded. A Staging operator must create the three EnterpriseUsers
through the real OIDC/Auth Gateway flow and then use the controlled one-time
bootstrap with approved company master data.

## Delivered model

| Area | Authoritative records |
| --- | --- |
| Group | GroupProfile (single row), LegalEntity, LedgerBook |
| Organization | BusinessUnit, Department, Warehouse, Salesperson |
| Parties | Customer, Supplier |
| Products | Product, SKU, ProductCategory, UnitOfMeasure, Brand |
| Identity mapping | Existing EnterpriseUser UUID, never name/email matching |
| Authorization | Role, RolePermission, UserRole |
| Data scopes | LegalEntity, Warehouse, Customer, Supplier, Brand, BusinessUnit |
| Policy | AssignmentPolicy, ApprovalPolicy |
| Control | AuthorizationRevision, append-only audit, transactional outbox |

The deployment database is the customer-group isolation boundary. No Business
Core table contains `tenant_id` or `client_group_id`.

## Decision flow

An exact object decision is the conjunction of:

```text
active EnterpriseUser
  + active assigned role
  + required permission key
  + every scope dimension carried by the target object
  + active target object
```

For example, warehouse access requires the user's LegalEntityScope,
WarehouseScope, and BusinessUnitScope all to cover the warehouse. A customer
requires LegalEntityScope, CustomerScope, and BusinessUnitScope. Product and
SKU access additionally binds BrandScope when the product has a brand.

Assignee and approver queries first check the caller's directory permission and
scope on the target, then select active users by exact role and permission,
then apply each candidate's own target scopes. Approval policies can prohibit
self-approval, require a different business-unit scope, and increase the
minimum approver count at a monetary threshold.

## Security and consistency controls

- Closed resource and scope enums; no caller-provided table, method, URL, or SQL.
- Service credential comparison uses a SHA-256 digest and constant-time equality.
- Actor and target identities are UUIDs referencing `enterprise_users`.
- Cross-user authorization reads require `business_authorization:read_all`.
- Administrative mutations require `business_core:admin`.
- Mutations lock and compare the global authorization revision; stale writes
  fail with 409 and cannot silently overwrite a newer policy state.
- Audit rows reject update and delete in PostgreSQL.
- Audit and outbox records commit atomically with authorization changes.
- Bootstrap is disabled by default, actor-bound, single-use, strict-schema, and
  all-or-nothing.

## B1 verification evidence

The automated disposable-PostgreSQL scenario covers:

```text
1 group
2 legal entities and primary ledger books
2 business units
2 warehouses
20 SKUs
5 customers
3 suppliers
3 active EnterpriseUsers
```

It proves both allow and deny outcomes for warehouse scope, role and permission
materialization, stable scope hashes, assignee resolution, revision conflict
handling, HTTP service-auth enforcement, audit tamper rejection, and the
single-group schema rule.

## Explicitly deferred

B1 does not implement sales orders, purchase orders, inventory movements,
receivables, payables, settlement, order profit, accounting journals, invoices,
bank connectivity, tax, manufacturing, mobile clients, or multi-customer SaaS.
It also does not switch `business-read-api` away from its current adapter. Those
changes belong to B2-B5 after their authoritative state machines and facts
exist.

## B2 handoff

B2 may now reference the B1 UUIDs directly and must use the access-check and
candidate APIs for sales commands. New transactional modules should share the
same PostgreSQL transaction, audit, outbox, expected-version, and idempotency
conventions; they should not add a parallel user directory or another scope
allowlist.
